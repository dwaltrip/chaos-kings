# custom-algo-2 — Context Doc

## Problem statement

**Core game mechanics (quick refresher):**

- General produces +1 troop every 2 ticks (first production on tick 2: 1 army → 2 army)
- Moving from tile A to adjacent tile B sends all-but-one troops from A to B. Moving into an already-owned tile sums armies.
- So a burst of N troops can capture a chain of N-1 empty tiles

**The perfect-start problem:** Find a move sequence for round 1 (50 ticks) that maximizes tiles captured.

The standard opening strategy is a **burst pattern**: accumulate troops on the general over several production ticks, then deploy them as a sequential set of moves to capture empty tiles. This repeats ~3-6 times across the 50 ticks. For example, `[10, 8, 4, 2]` achieves a perfect start (24 tiles captured) on a sufficiently open board where the general has all 4 neighbors free. The set of feasible burst patterns (burst lengths, timing, overlap allowances) can be pre-computed from the production schedule and tick budget.

The solver must choose both the burst pattern and the path for each burst, given the board geometry (mountains, obstacles, board edges). Most boards have many equally-optimal solutions — we just need to find one. But the naive search space is enormous (brute force infeasible), so the core challenge is pruning to the good parts efficiently.

## The three-region mental model

The board around the general can be thought of as three loose regions:

- **Near-region** — tiles close to the general where multiple bursts overlap. Handled by prefix-path generation.
- **Mid-region** — tiles further out, reached only by the longer bursts. Handled by lane decomposition — partitioning this space into non-overlapping lanes.
- **Far-region** — unreachable within the tick budget. Ignored.

Together, the near-region and mid-region make up the "starting-region": tiles that can be reached during the opening round.

These aren't hard boundaries coded into the solver — they're a conceptual tool for reasoning about how the problem decomposes. The actual near/mid boundary emerges from the prefix-path and lane-decomposition stages.

## Solver approach

**Why not brute-force path search?** The number of non-backtracking paths from the general grows exponentially with length:

Non-backtracking paths from the general on an open board[^1]: ~300 at length 6, ~16K at length 10. Even just 4 bursts of length 6 = ~300^4 ≈ 8 billion combinations.

`custom-algo-1` (the previous solver) iterates captured-tile targets downward (try for 24 captured, then 23, etc.) and uses grouped backtracking with bitmask feasibility pruning. It prunes well on many boards, but still grinds through millions of combinations on poorly-performing boards[^2].

**custom-algo-2's approach:** Split the problem into two mostly-independent sub-problems:

1. **Prefix generation (near-region)** — How to get off the general into good positions. Small search space, topology-dominated. Enumerate sets of short prefix paths (one per burst, depth ~3-4), all starting at the general.

2. **Lane construction (mid-region)** — Given prefix tips as starting positions, construct expansion paths for the ~1-2 bursts that extend beyond the near-region. Larger search space, but simpler local structure — once you're in open enough space, the hardness is combinatorial rather than navigational.

The interface: **prefix tips are lane starting positions.**

**The key insight (4.10-6):** Prefix quality is dominated by whether the tip can support a lane of the required length. This means one shared scoring layer — measuring "can a good lane extend from this tile?" — serves both sub-problems. Every investment in the scoring layer pays off on both sides.

## Status

**Overall:** Early prototyping / brainstorming phase. Components are being explored individually before integration. The core framing (two-problem decomposition, shared scoring layer) still feels strong — the next step is exploring concrete implementation ideas and iterating toward a working solver prototype.

**Lane decomposition:**

- Exhaustive enumerator validated as tractable for small cases — useful for validating other approaches, but hits the same combinatorial ceiling on real boards.
- Greedy lane construction is promising and could anchor an initial solver prototype, especially with added backtracking and/or heuristics.

**Prefix generation:**

- Simple first-pass enumerator exists, needs more work.
- Scoring: ray-depth prototype is decent for how basic it is. The other scoring signals (divergence, articulation points) aren't contributing much.
- Key ambiguities remain: how should prefix path lengths vary? How to define the space of allowed overlap during generation?
- Haven't yet engaged with several "known tensions" from the framing docs (e.g. per-tip vs. joint quality, extreme geometries).

**End-to-end integration:** Not yet attempted.

Progress on either sub-problem is likely to help the other, given the shared scoring layer.

## Code

### Solver prototype (`custom-algo-2/`)

- `prefix-gen/` — Prefix-set enumeration and scoring. Enumerates K-tuples of short paths from the general, scores by tip quality. Early prototype — scoring needs refinement.
- `lane-decomp/` — Mid-region lane decomposition prototyping. Includes exhaustive enumerator, heuristic approaches (face-projection, greedy-longest-path), and evaluation harness. Greedy heuristic shows promising recall vs. exhaustive oracle. Uses "blobs" (random-walk generated tile sets) as stand-ins for actual prefix-path output to explore lane-decomp in isolation.

### Shared infra (`perfect-start-solver/`)

- `starting-region/` — Topological analysis of the region near the general. BFS-bounded tile set with per-tile annotations (distance, divergence, ray depth). `tip-scorer.ts` scores prefix tips using these signals.
    - TODO: cleanup — move custom-algo-2 specific parts down, drop articulation points, fix face-projection toward-general issue (see `4.12-2-code-cleanup-notes.md`)

- `test-boards.ts` — Board registry with categorized lists (realistic, simple, slow-search, slow-pathgen). Entry point for loading boards by name.
- `test-boards-data/` — Board fixture files (simple synthetics, 25x25, 30x30 realistic).
- `utils/board.ts` — Board loader (by name from test-boards-data). Converts to `FlatBoard`, the core perf-efficient board type used throughout.
- `utils/parse-board.ts` — Parse board strings to `BoardState`.
- `utils/render-board.ts` + `render-board-cli.ts` — ASCII board visualization with annotation overlays.
- `utils/board-graph.ts` — Graph analysis: Tarjan articulation/bridges, BFS helpers, neighbor utilities.
- `utils/bfs-distance-field.ts` — Distance field computation from a start tile.
- `utils/frontier.ts` — Get boundary tiles of a claimed region.
