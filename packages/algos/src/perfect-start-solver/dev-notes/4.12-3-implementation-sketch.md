# Implementation Sketch — custom-algo-2 prototype solver

Concrete module breakdown, interfaces, and pseudocode for the prototype solver. Companion to the [design doc](4.12-2-prototype-solver-design.md).

---

## Module overview

| Module | Responsibility |
|---|---|
| **Lane builder** | Given (tip, length) pairs + obstacle mask, construct lanes via greedy DFS. Tries M! orderings. |
| **Burst-path mapper** | Given a prefix set + timing entry, find valid burst→prefix-path assignments with overlap verification. |
| **Solution assembler** | Stitch prefix paths + lanes into full solution. Validate timing and totals. |
| **Prefix pool** | Generate scored prefix sets for a given overlap budget. Encapsulates config iteration. |
| **Orchestrator** | Top-level solver. Drives the nested loops, early-terminates on first solution. |
| **CLI runner** | Entry point. Parses args, calls orchestrator, prints results. |

## Interfaces

### Lane builder

```ts
interface LaneRequest {
  tip: number;       // prefix tip tile — lane starts here
  length: number;    // required lane length (new captures)
}

interface LaneResult {
  lanes: Lane[];     // one per request, positionally matched
}

function buildLanes(
  board: FlatBoard,
  requests: LaneRequest[],
  obstacleMask: bigint,       // prefix union + general
): LaneResult | null
```

Internally: tries all M! orderings of requests. For each ordering, greedy DFS per lane (first path found wins, mark tiles used). Returns first success or null.

**Tip vs. lane boundary:** The tip is the last tile of the prefix path — it's a prefix tile, counted in prefix length and included in the obstacle mask. The lane extends *beyond* the tip into fresh territory. So the lane builder starts DFS from walkable neighbors of the tip (not the tip itself), calling `findPath(board, neighbor, laneLength, obstacleMask)` for each. `findPath` stays generic (always includes start tile in result). The tip→neighbor indirection is lane-builder logic.

Written fresh (not a modification of the existing `greedyDecompose`). Reuses `findPath` — a clean "non-backtracking path of exact length from a start tile, avoiding obstacle mask" DFS — pulled out of `greedy-longest-path.ts` into a shared utility.

### Burst-path mapper

```ts
interface BurstAssignment {
  burstIndex: number;         // position in timing entry (departure order)
  prefixPath: PrefixPath;     // assigned prefix path
  laneLength: number;         // 0 = burst contained in prefix, >0 = needs lane
}

function mapBurstsToPaths(
  prefixSet: PrefixSet,
  timingEntry: TimingEntry,
): BurstAssignment[][]        // array of valid complete assignments
```

**Key invariant:** A prefix set's total overlap (sum of path lengths - |union|) must equal the timing entry's total overlap (sum of `overlaps[]`). This is why the orchestrator filters by `arraySum(e.overlaps) === prefixSet.overlap` — a prefix set with overlap N can only work with timing entries whose per-burst overlaps sum to exactly N.

Internally: recursive enumeration in departure order. At each step:
- Try assigning the current burst to each unused prefix path
- Check geometric overlap (tiles in path already captured by earlier bursts) matches `timingEntry.overlaps[i]`
- Compute `laneLength = captures[i] - (prefixLength - prefixOverlap)`, where `prefixOverlap` is the geometric overlap just verified — it equals `timingEntry.overlaps[i]` for a valid assignment
- Prune if laneLength < 0
- If all bursts assigned, emit the complete assignment

### Solution assembler

```ts
interface SolvedBurst {
  path: number[];             // full path: prefix tiles + lane tiles (no general)
  captures: number;
  overlap: number;
  startTick: number;
  endTick: number;
}

interface Solution {
  captures: number;           // total new tiles captured
  bursts: SolvedBurst[];      // in departure order
  endTick: number;
}

function assembleSolution(
  assignments: BurstAssignment[],
  lanes: Lane[],              // parallel to assignments with laneLength > 0
  timingEntry: TimingEntry,
  maxTicks: number,
): Solution | null             // null if validation fails
```

Stitches each burst's prefix path + lane into a full path. Runs timing simulation (`simulateSpecs`) to get per-burst tick ranges. Sanity-checks: total captures match, no tile conflicts, fits within maxTicks.

### Prefix pool

```ts
function generatePrefixPool(
  board: FlatBoard,
  general: number,
  maxTotalOverlap: number,
  topK: number,
): PrefixSet[]
```

Encapsulates the `prefixLengths` config iteration internally — enumerates configs across burst counts (3-6) and path lengths (1-5), deduplicates by union mask, returns top-K scored sets up to the overlap budget. The number of internal configs is derived from these ranges, not a separate parameter.

**NOTE:** The design doc frames overlap budget as the outermost conceptual dimension (generate per overlap value for clean separation). For the prototype, we fold this into prefix-gen: generate once with a max overlap budget, and the orchestrator filters by `sum(entry.overlaps) === prefixSet.overlap` during matching. If this leads to poor coverage of low-overlap solutions (top-K heap dominated by high-overlap sets), we can switch to per-value generation.

## Orchestrator pseudocode

```ts
function solve(board: FlatBoard, general: number): Solution | null {
  // Setup (once per board)
  const region = buildStartingRegion(board, general);
  const annotations = computeCustomAnnotations(region, board);
  const tipScores = scoreStartingRegion(region, annotations);
  const prefixSets = generatePrefixPool(board, general, MAX_OVERLAP, TOP_K);

  for (let target = MAX_CAPTURES; target >= MIN_CAPTURES; target--) {
    const timingEntries = buildTimingEntries(target, TIMING_CONFIG);

    for (const prefixSet of prefixSets) {
      // Filter timing entries by compatibility
      const compatible = timingEntries.filter(e =>
        e.captures.length === prefixSet.prefixes.length &&
        arraySum(e.overlaps) === prefixSet.overlap
      );

      for (const entry of compatible) {
        const assignments = mapBurstsToPaths(prefixSet, entry);

        for (const assignment of assignments) {
          // Extract lane requests for mid-region bursts
          const laneRequests: LaneRequest[] = [];
          for (const a of assignment) {
            if (a.laneLength > 0) {
              laneRequests.push({ tip: a.prefixPath.tip, length: a.laneLength });
            }
          }

          const obstacleMask = prefixSet.unionMask | (1n << BigInt(general));
          const result = buildLanes(board, laneRequests, obstacleMask);
          if (!result) continue;

          const solution = assembleSolution(assignment, result.lanes, entry, MAX_TICKS);
          if (solution) return solution;
        }
      }
    }
  }

  return null;
}
```

## Open implementation details

**Types: general-excluded convention applied at the source.** The existing `prefix-gen/generate.ts` will be modified in-place to exclude the general from paths, masks, and lengths. This is a mechanical change (~25 lines): adjust `enumeratePathsFromStart` to start DFS from neighbors, lower `prefixLengths` minimum from 2 to 1, change overlap floor from K-1 to 0. Two research scripts (`compare-blob-sources.ts`, `dump-prefix-sets.ts`) need trivial updates. No production code is affected.

**Prefix pool builder is additive.** A new `generatePrefixPool` function wraps the existing `generatePrefixSets` — loops over burst count/length configs, calls the generator for each, merges results with cross-config union-mask dedup. The generator's algorithmic core (DFS enumeration, K-tuple overlap pruning, top-K heap) is reused as-is.

**Mapper returns assignments eagerly.** For the prototype, `mapBurstsToPaths` returns the full array of valid assignments. If this becomes a bottleneck (too many valid assignments for some inputs), switching to a generator/iterator is a natural optimization.

**Overlap is fully within prefix paths.** The mapper determines overlap using only prefix path tiles — lanes don't exist yet at mapping time. This is correct by design (lanes are in fresh mid-region territory), but see the design doc's conventions section for a possible limitation on very constrained boards.

**TimingEntry is used as-is, no convention conversion needed.** The existing `captures[]` counts new tiles (excluding general), `overlaps[]` counts re-traversals (excluding general). `moves = captures + overlap` = total tiles traversed = `prefixLength + laneLength` under our convention.

**Prefix pool config values are first-pass guesses.** Path length range (1-5), burst counts (3-6), and topK (20-50) are educated guesses. The right values will come from running on real boards and iterating.
