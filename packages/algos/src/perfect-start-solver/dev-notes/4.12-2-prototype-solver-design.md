# Prototype Solver Design — custom-algo-2

Design doc for the initial end-to-end solver prototype. Emerged from a design conversation on 2026-04-12. The goal is a working pipeline that produces optimal (or near-optimal) solutions, with known gaps that we iterate on once it runs.

Reference: [context doc](4.12-1-custom-algo-2-context-doc.md) for problem statement, three-region mental model, and existing code inventory.

---

## Relevant mechanics

- General produces +1 troop every 2 ticks (first production on tick 2).
- Moving from tile A to adjacent tile B sends all-but-one troops from A to B.
- Moving across already-owned land is free — no troop cost, the tile already has at least 1 troop.
- Movement doesn't interfere with production. For each tick, moves are processed *before* the any production occurs.

## Conventions

- **Burst length = captures (new tiles).**
   - Because traversing owned land is free, the number of new tiles is what determines troop cost.
   - A burst may also re-traverse owned tiles ("overlap"), so `total_moves` (and `total_ticks`) equals `captures` + `overlap`.
- **All lengths and tile counts exclude the general.**
   - The general is the implicit start of every burst — never counted in path lengths, overlap, or tile sets.
   - Some existing code/docs may be inconsistent — new code follows this strictly.

---

## Key insights

**Prefix sets are geometry, timing entries are timing.** Prefix paths describe how to exit the general's neighborhood — pure board topology, independent of capture target. Computing them once and reusing across all targets is a clean separation.

**Overlap bridges geometry and timing.** Prefix sets are unordered — they're just K paths from the general, with some spatial overlap structure that falls out naturally during enumeration. Timing entries are ordered — each burst has a specific overlap count. The burst→prefix-path mapper is where these meet: it assigns bursts to prefix paths and checks that the per-burst overlaps match. This means prefix generation only needs a **total overlap budget** (a single number), not per-burst overlap specs. The per-burst breakdown is the mapper's job.

**Burst-to-path mapping must be sequential.** You can't verify burst 3's overlap without knowing what bursts 1-2 captured. Building the mapping in departure order turns K! enumeration into a pruning tree where invalid overlaps are caught early.

**Lane construction is cheap because K is small.** Only 2-3 bursts extend into mid-region. M! orderings = 2-6 attempts per mapping. Binding each lane to its prefix tip is simpler than searching all frontier tiles.

**The prototype will surface the real bottlenecks.** Overlap config space, prefix-gen params, pre-compute vs. on-demand — we have reasonable first-pass strategies for all of these, but the right answers come from running on real boards.

## Pipeline

```
Total overlap budget (0..~10)
│
├─ Generate prefix sets up to this budget (top-K scored)
│
└─ For each capture target (24, 23, 22, ...):
   │
   └─ For each prefix set:
      │
      └─ For each compatible timing entry (~5700 total, filtered by overlap):
         │
         └─ Map bursts → prefix paths (sequential, overlap verification):
            │  - Process in burst departure order
            │  - Check geometric overlap matches timing entry's overlaps[i]
            │  - Compute lane_length per burst
            │  - Prune if lane_length < 0
            │
            └─ Lane construction (greedy, M! orderings):
               │  - Each lane bound to its prefix tip
               │  - Obstacle mask = prefix union + earlier lanes
               │  - First success → solution found, done
```

**Complexity note:** The burst→path mapping (up to K! permutations, heavily pruned by length/overlap compatibility) and the lane construction ordering (M! for M mid-region bursts) are **independent multiplicative factors** — a different mapping changes *which* tips the lanes start from, while a different ordering changes *which lane gets built first*. Both matter for whether greedy succeeds. We expect K! to be heavily pruned in practice, and M! ≤ 6, so the combined cost should be manageable.

### Stage details

**1. Starting region + annotations + tip scores** — Already built. Computed once per board. Feeds into prefix-gen scoring.

**2. Prefix-set generation** — quick prototype built, needs param tuning (and later refinement)

* Run the generator with various `prefixLengths` configs (path lengths 1-5, burst counts 3-6) and overlap budgets.
* Different configs are an implementation detail of the prefix-gen module — other code simply receives a sequence of scored prefix sets for a given overlap config.
* Top-K for the alpha prototype, full enumeration as a top priority for follow-up work.

**3. Timing entries** — Already built (`buildTimingEntries` in custom-algo-1). ~5700 entries for 24 captures with max-overlap-per-burst=4. Iterate all, filtered by compatibility with the current overlap config.

**4. Burst-to-path mapping** — New code. For a given (prefix set, timing entry) pair, try assigning each burst to a prefix path:

- Process bursts in departure order (burst 1 first)
- At each step, track which tiles are captured so far
- For burst i assigned to path j: verify that the geometric overlap (tiles in path j already captured) equals `overlaps[i]` from the timing entry
- Compute lane length: `lane_length = burst_length - (prefix_length - prefix_overlap)`. If negative, burst can't use this path. If zero, burst is entirely within the prefix (no lane needed).
  - Example: burst with 8 captures, 2 overlap. Prefix length 4, prefix_overlap 2. → `lane_length = 8 - (4-2) = 6`. New captures: 2 (prefix) + 6 (lane) = 8.
- This is a recursive enumeration with early pruning, not a flat K! loop

**5. Lane construction** — Existing greedy decomposer, modified interface. For the M bursts (typically 2-3) that extend into mid-region:
- Each lane starts from its prefix tip (bound, not searched)
- Try all M! orderings of lane construction
- Greedy DFS from tip, obstacle mask = prefix union tiles + earlier lanes' tiles
- First ordering that succeeds → solution

**6. Solution assembly** — New code. Combine prefix paths + lanes into full per-burst paths. Validate timing. Output in a format comparable to custom-algo-1's `Solution` type.

### Failure strategy

When the pipeline fails to find a solution at the current capture target with the current prefix pool:

1. **Expand prefix pool** — increase topK, try more `prefixLengths` configs, relax overlap budgets
2. **Full prefix enumeration** — drop scoring filter entirely, enumerate all valid prefix sets with safe-only pruning (deferred from alpha, but first priority follow-up)
3. **Lower capture target** — try 23, then 22, etc. Same descent strategy as custom-algo-1.

## Interface changes to existing modules

**Greedy decomposer** (`lane-decomp/greedy-longest-path.ts`):
- Current: takes `Blob` (tiles + mask), computes frontier internally, searches all frontier tiles per lane
- New: takes explicit entry tiles + obstacle mask. Each lane is bound to a specific entry tile.
- Existing analysis code (blob-based evaluation) passes `getFrontier(board, blob.tiles)` to preserve current behavior.

**Prefix generator** (`prefix-gen/generate.ts`):
- Current: takes fixed `prefixLengths[]` array (tile counts including general), `maxOverlap`
- Needs: path lengths that exclude the general (convention fix). Multiple runs with different configs to build the prefix pool.
- Open: whether to rework for mixed lengths in a single enumeration, or keep multiple runs. Multiple runs is simpler for the prototype.

## What's deferred

- **Saved tiles** — tiles reserved near the general for a final small burst. Not modeled in the prototype. May affect prefix-gen constraints.
- **Corridor-model DAG** — the explore-landscape equivalence machinery for collapsing mid-region search. The prototype uses greedy lane construction instead.
- **Variable prefix depth per direction** — all paths in a config share the same length options. Asymmetric boards might benefit from deeper prefixes in constrained directions.
- **Greedy backtracking within lanes** — trying alternative DFS paths when downstream lanes fail. Natural follow-up to the M! ordering approach.
- **Full prefix enumeration fallback** — the alpha uses top-K only. First priority after getting it working.

## Open questions

- **Overlap config space:** Prefix generation is parameterized by **total overlap** (a single number, 0..~10)[^1] — the per-burst breakdown is handled downstream by the burst→path mapper. More specific parameterization (per-path overlap profiles) could help the generator prune, but adds config complexity (~40-50 unordered profiles vs. ~11 total values). Start with total-only and revisit if the mapper rejects too many sets.
- **Pre-compute vs. on-demand:** Generate all prefix sets upfront for all overlap configs, or lazily as needed? Depends on how large the prefix pool gets.
- **Prefix-gen params:** How many `prefixLengths` configs, what path length range, what topK? First-pass guesses: path lengths 1-4, topK 20-50, 10-20 configs. Will iterate based on results.
- **Timing entry filtering:** How efficiently can we filter timing entries by overlap compatibility with a prefix set? May want an index structure if the naive loop is too slow.
- **Timing entry ranking:** Currently no ranking — we iterate all ~5700 entries. A ranking (e.g. by overlap budget, burst count) could let us try likely-successful entries first and short-circuit. Worth exploring once the prototype runs.
- **Evaluation harness:** Need to compare prototype results against custom-algo-1 on the test board suite. Metrics: capture count match, solve rate, runtime.

[^1]: Estimates from Daniel's gameplay experience and napkin math, not exhaustive analysis. Difficult boards (lower capture targets) may need higher overlaps.
