# Session 2 — Lane Decomposition Heuristics vs. Oracle (Summary)

Short refresher. Full context, traces, and caveats in [session 2 findings](4.10-3-lane-decomp-session-2-findings.md). Prior work: [session 1 findings](4.10-1-lane-decomp-session-1-findings.md).

## What we did

Evaluated two cheap heuristics against the session 1 exhaustive enumerator (oracle):

- **Face projection** — straight-ray feasibility filter from each frontier tile.
- **Plain greedy** — sort lane lengths descending, DFS a path of exact length from frontier tiles, first path wins, no cross-lane backtracking.

Matrix: **7 boards** (3 tight-toy, 2 tight-realistic, 2 less-constrained) × **4 seeds** × **3 profiles** (`[5,3]`, `[6,4,3]`, `[8,6,4]`) = **84 cells**. Ran twice under two blob configurations ("baseline" and "reach-more") — see findings §5 for why.

## Headline results (reach-more blob config)

| Metric | Value |
|---|---|
| Oracle exists | 76/84 (90%) |
| **Greedy recall** | 67/76 (88%) |
| **Face precision** (in this matrix) | 58/58 (100%) |
| Face recall | 58/76 (76%) |
| Face false positives | 0 |

## Four findings

1. **Face projection is a safe one-sided filter.** 100% precision across 84 cells — every "feasible" verdict matched the oracle. Misses turning-lane geometries where straight rays can't express reachable depth (canonical example: `scattered-pockets-13x13`, where every lane must turn to exit the tube). → findings §3

2. **Plain greedy is surprisingly decent.** 88% recall on realistic blobs. 8 of 9 misses live on `pocket-11x11`, driven by a DFS ordering lock-in: the first length-L path found eats tiles a later shorter lane needs. The 9th miss (`tight-edge-with-chokes` seed 4, long) is the same structural issue in a different guise. A face-projection-seeded DFS order or single-lane backtracking should close most of the gap. → findings §4

3. **The biggest reframe — blob pathology.** Session 1's "tight regime hardness" was partly an artifact of the random-walk blob generator, not the board. Small blobs collapsed into tight pockets, stranding the frontier inside. Bumping per-path reach pushed frontiers into open space and flipped 8 oracle-fail cells to feasible with no algorithmic change. Real prefix sets would spread wider still. → findings §5

4. **One board is genuinely hard.** `3.21-real-board-tight-corner-1` at medium and long profiles remains oracle-infeasible under every random-walk blob we tested in both configurations. Session 1's "chute near (22, 17-21)" is the mechanism — long lanes in our tested blobs all ended up colliding inside it. **Not a claim about the board's 24-capture optimality, overall solvability, or feasibility under different prefix sets** — see findings §6 for the full scope statement. → findings §6

## Next-step candidates

- **Face-projection-seeded greedy** — use the depth map to order the greedy DFS. Expected to close most `pocket-11x11` cases cheaply.
- **Length-aware max-flow filter** — a second filter tier that can catch chute-collision cases face projection misses (like `tight-corner-1` medium/long).
- **Realistic prefix blobs** — replace random-walk generator with hand-picked or prefix-enumerator output. Biggest validity lift for the next session.
