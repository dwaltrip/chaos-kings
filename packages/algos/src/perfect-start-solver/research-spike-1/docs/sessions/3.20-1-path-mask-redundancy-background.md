# 1.3 Path Mask Redundancy — Background & Motivation

## What's happening today

The solver generates all non-backtracking paths from the general up to length 12 via DP (`genPathsDP`). On open-11x11 that's ~60K paths. Each path carries `tiles: number[]` and `mask: bigint`.

In the search inner loop, the key check for zero-overlap bursts is:

```ts
if ((cand.mask & coveredMask) !== 0n) continue;
```

Only the mask matters — tile order is irrelevant. Two paths with different tile orderings but the same mask are completely interchangeable for this check. The solver doesn't know this — it checks each one individually.

For overlap bursts, tile order matters, but only the prefix (the first `overlap` tiles that retrace owned territory). So the effective identity is `(mask, prefix[0..overlap])`, still much smaller than all paths.

## Why this analysis matters

### Immediate payoff — dedup (4.1)

If 60K paths collapse to, say, 3K distinct masks, dedup is a near-free 20x reduction in candidates checked. No solver logic changes needed, just a filtering step after `buildPathEntries`.

### Enables a fundamentally different search structure

The critical review points out that a deduplicated mask set can be organized as an inverted index: for each tile, which masks contain it? When a tile gets covered, walk the index to invalidate affected masks — O(masks-per-tile) instead of O(all-candidates). This changes the inner loop's complexity class, not just its constant factor.

### Informs constraint propagation feasibility

Arc consistency (pruning burst-pair incompatibilities before search) is O(d²) per pair where d = domain size. If dedup shrinks domains from 60K to 3K, AC-3 goes from intractable to cheap. The redundancy numbers directly determine whether CSP techniques are viable.

### Tells us where redundancy lives

The per-length, per-board breakdown shows whether redundancy is concentrated in long paths (where the DP explosion happens) or distributed evenly. This shapes whether dedup alone is enough or whether we also need clustering (4.2) or lazy generation.

## What we want to learn

1. **Compression ratio by board and path length** — the headline number. How much redundancy is there?
2. **Distribution shape** — a few mega-classes (100+ paths per mask) or many small ones? Affects whether dedup or clustering is the right tool.
3. **Overlap-aware equivalence** — for overlap paths, how much does adding prefix info inflate the class count beyond pure mask dedup?
4. **Dominated paths** — paths whose mask is a strict subset of another same-length path's mask. These are strictly worse and can always be pruned. How many exist?
5. **Board topology correlation** — do open boards have high redundancy and constrained boards low? Or is it more nuanced?

## What we're NOT doing yet

- Actually implementing dedup (that's 4.1, a follow-up)
- Changing the solver in any way
- Building inverted indexes or constraint propagation

This is pure measurement. The output is numbers and tables that inform what to build next.
