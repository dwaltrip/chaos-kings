# Neighbor partitioning: the three levels

Session 3.20-2. Explains how neighbor partitioning works at each level of ambition and how they build on each other.

## The core observation

After `buildPathEntries` strips the general tile, each `PathEntry.tiles[0]` is a neighbor of the general — the direction the burst goes. Every burst must start through one of these neighbors, and this starting neighbor determines which candidates are relevant.

Two rules govern the filter:
- **Zero-overlap burst**: `tiles[0]` must NOT be in `coveredMask` (otherwise the path overlaps with existing territory).
- **Prefix-overlap burst**: `tiles[0]` MUST be in `coveredMask` (it's part of the overlap prefix — the burst retraces existing tiles before branching into new ones).

## Level 1: Partition-and-filter (implemented)

Pre-group candidates into `Map<moveLen, Map<neighbor, PathEntry[]>>`. At each search depth, skip partitions that can't work:

```
for (const [neighbor, partition] of partitionsAtLen) {
  if (overlap === 0 && neighborCovered) continue;    // skip covered
  if (overlap > 0 && !neighborCovered) continue;     // skip uncovered
  for (const cand of partition) { /* full mask check */ }
}
```

The search still discovers which neighbor each burst uses implicitly — by trying candidates across all compatible partitions and seeing what sticks. Level 1 just avoids iterating candidates that would definitely fail on their first tile.

**Result**: 1.28–1.41x speedup on hard corner boards (degree-2 generals), 50% candidate reduction. Mild overhead on easy boards where candidate scanning isn't the bottleneck. See `findings/3.2-neighbor-partitioning-level-1.md`.

## Level 2: Explicit neighbor assignment

Key insight: **each zero-overlap burst must go through a distinct neighbor.** Two zero-overlap bursts can't share `tiles[0]` — that tile would be in both paths, creating overlap. The Level 1 solver discovers this through trial and error (try a candidate, fail the mask check, move on). Level 2 makes it explicit.

Before searching, enumerate valid burst→neighbor assignments. For a timing entry with captures `[12, 8, 4]` and overlaps `[0, 0, 0]` on a degree-4 general (neighbors A, B, C, D):

```
burst-1→A, burst-2→B, burst-3→C
burst-1→A, burst-2→B, burst-3→D
burst-1→A, burst-2→C, burst-3→B
... (P(4,3) = 24 permutations)
```

For each assignment, the search at each depth goes to **one specific partition** instead of iterating all compatible ones.

### Where the extra wins come from

1. **Upfront assignment pruning.** Before scanning any candidates: does partition C have any paths at length 4? If not, eliminate all assignments that put a burst through C at that length. Free.

2. **Per-neighbor feasibility.** Today's feasibility checks are global (total blank tiles within reach of the general). With explicit assignments, you can check: does the territory behind neighbor B specifically have enough blank tiles for the burst assigned to it? This is tighter — it catches "enough tiles overall, but not enough in B's direction."

3. **Cleaner backtracking.** Level 1 mixes neighbor exploration with candidate exploration: try candidates through B, then C, then D at each depth. Level 2 separates these concerns: exhaust assignment (B, C) before moving to (B, D). The search explores one spatial arrangement at a time.

### Overlap bursts in assignments

Overlap bursts don't consume a new neighbor — they reuse one. If burst-2 has overlap=1, its `tiles[0]` must be in `coveredMask`, meaning it follows a previous burst's path. The assignment for overlap bursts is constrained to already-used neighbors, reducing the permutation count.

### Cost

The assignment loop adds P(D, K) permutations where D = general's degree and K = number of zero-overlap bursts. Typical values:
- Degree-2 (corner), 2 zero-overlap bursts: P(2,2) = 2
- Degree-4 (center), 3 zero-overlap bursts: P(4,3) = 24
- Degree-4, 4 zero-overlap bursts: P(4,4) = 24

These are small numbers. The structure they add is worth far more than the iteration cost.

## Level 3: Timing-driven assignment (full pipeline)

The version from STATUS: timing entry → neighbor assignment → per-partition search.

The difference from Level 2: instead of enumerating assignments generically, the timing entry's structure constrains which assignments make sense. A timing entry with captures `[12, 4, 4, 4]` needs one neighbor with deep territory (for the 12-burst) and three with shallow territory. You can match bursts to neighbors based on how much open space each direction has.

This is where spatial awareness enters. Level 2 asks "is this assignment valid?" Level 3 asks "is this assignment *good*?" — ranking or pruning assignments by how well each burst's needs match each neighbor's capacity.

This gets into heuristic territory and is the entry point to the sector awareness that the research spike is ultimately about.

## How they build on each other

| Level | What changes | Win type | Data structure |
|---|---|---|---|
| 1 (done) | Skip irrelevant partitions | Fewer candidates iterated | `Map<moveLen, Map<neighbor, PathEntry[]>>` |
| 2 | Fix burst→neighbor upfront | Prune bad assignments, tighter feasibility | Same + assignment enumeration |
| 3 | Timing-driven assignment | Match burst needs to neighbor capacity | Same + per-neighbor spatial metrics |

Each level reuses the `PartitionedEntries` map from Level 1. The progression is additive — each level wraps the previous one with more structure.
