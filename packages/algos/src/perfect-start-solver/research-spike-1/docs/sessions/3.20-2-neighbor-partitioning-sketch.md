# Neighbor partitioning experiment sketch

Session 3.20-2. Design sketch for the pipeline idea from STATUS (timing entry → neighbor assignment → path partitioning → per-partition search).

## Three levels of ambition

The pipeline can be built incrementally. Each level subsumes the previous:

**Level 1 — Partition-and-filter.** Pre-partition candidates by `tiles[0]` (starting neighbor). In the search loop, only scan partitions where the starting neighbor is compatible with `coveredMask`. Same search structure — just fewer candidates scanned. ~30 lines of new logic (plus harness code and imports from the solver internals).

**Level 2 — Explicit neighbor assignment.** Enumerate burst→neighbor assignments upfront (e.g., "burst-1 → A, burst-2 → B, burst-3 → C"), then search within each assignment's partitions. Adds earlier pruning — if neighbor B has too few paths at the required length, skip that assignment without scanning. Costs an extra assignment loop (P(4,3) = 24 permutations for 3 zero-overlap bursts on degree-4). Restructures the solver's control flow.

**Level 3 — Full pipeline.** Each partition becomes a self-contained sub-problem. Timing entry drives neighbor assignment drives partition search. The version described in STATUS. Subsumes Levels 1 and 2.

**We're starting with Level 1.** It's the lowest-risk entry point — no structural changes to the search, just a filtering optimization. If it shows measurable speedup, Level 2 is the natural next step (the partitioned data structure carries over). If it doesn't, we've learned that candidate scanning isn't the bottleneck — same signal as 1.2 phase timing would give, but from a real implementation instead of instrumentation.

## Goal

Measure whether Level 1 partitioning speeds up the solver on real boards.

## Background

After `buildPathEntries` strips the general tile, each `PathEntry.tiles[0]` is a neighbor of the general — the direction the burst goes. Today the solver scans all candidates at a given move length, regardless of direction. For zero-overlap bursts, any candidate whose `tiles[0]` is already in `coveredMask` will fail the overlap check. For overlap bursts, any candidate whose `tiles[0]` is NOT in `coveredMask` will fail the prefix check. Both are wasted iterations.

Neighbor distribution data from 3.20-1 shows this matters especially on asymmetric boards (2–4x imbalance across neighbors at length 12). Even on symmetric boards, skipping covered-neighbor partitions saves ~25% per depth level.

## The change

### Data structure

Partition `PathEntriesByLen` by starting neighbor:

```
type PartitionedEntries = Map<moveLen, Map<neighborTile, PathEntry[]>>
```

Build this once from the existing `PathEntriesByLen` by grouping on `tiles[0]`. Keep the original `PathEntriesByLen` too (or reconstruct full lists by concatenating partitions) — we need both for measurement comparison.

### Search loop change (in `searchGrouped`)

Today (lines 295–326 of `solver-v3.ts`):
```
for (const [key, bucket] of buckets) {
  const candidates = entriesByLen.get(moveLen);    // ALL candidates
  for (const cand of candidates) { ... }
}
```

With partitioning:
```
for (const [key, bucket] of buckets) {
  if (overlap === 0) {
    // only scan partitions where tiles[0] is NOT covered
    for (const [neighbor, partition] of partitioned.get(moveLen)) {
      if (coveredMask & (1n << BigInt(neighbor))) continue;  // skip covered
      for (const cand of partition) { ... }
    }
  } else {
    // only scan partitions where tiles[0] IS covered
    for (const [neighbor, partition] of partitioned.get(moveLen)) {
      if (!(coveredMask & (1n << BigInt(neighbor)))) continue;  // skip uncovered
      for (const cand of partition) { ... }
    }
  }
}
```

The inner candidate check is identical — we still do the full mask overlap/prefix check. The partition just skips candidates that would definitely fail.

### Burst-1 (outer loop in `solveV3`)

No change for Level 1. Burst-1 starts from an empty board, so all neighbors are available and no candidates can be skipped. (Symmetry breaking — fixing burst-1 to one neighbor on symmetric boards — is a separate optimization that stacks with this.)

## What to reuse from `solver-v3.ts`

The experiment needs its own version of `searchGrouped` (modified inner loop) and a `solveV3` wrapper to wire in the partitioned data structure.

Everything else should be imported directly. Currently `solver-v3.ts` only exports `solveV3`, `Solution`, `SolverConfig`, `SolverResult`. The experiment needs ~10 additional symbols that are currently private: `buildTimingGroups`, `EntryWithMoves`, `TimingGroup`, `precomputeBlankTileDistMasks`, `entryIsFeasiblePerBurst`, `entryIsFeasibleNeighbors`, `entryIsFeasibleAggregate`, `emptyStats`, `SearchStats`, `bucketKey`, `FEASIBILITY_MAX_DIST`, `DEFAULT_CONFIG`.

**Approach: export these from `solver-v3.ts`.** It's all additive (no behavior change), and avoids maintaining a ~150-line copy of the solver internals in the experiment. This also sets up clean imports for future experiments.

## Experiment design

**Script**: `experiments/3.20-2-neighbor-partitioning.ts`

**Method**: Run both original `solveV3` and the partitioned version on all 28 test boards. Compare:
- Wall clock time (5 warmup runs, 10 timed runs, take median; interleave boards to control for thermal effects)
- `stats.candidatesChecked` — direct measure of scanning reduction
- Solution validity — partitioned version must find a solution with equal or better capture count. The specific paths may differ (candidate iteration order changes across partitions), which is fine — we care about solution quality, not identity.

**Expected results**:
- `candidatesChecked` drops by 25–75% depending on board asymmetry and solution depth (25% is the idealized lower bound on symmetric degree-4 boards at depth 2; asymmetric boards and deeper searches save more)
- Wall clock speedup is smaller (feasibility checks and backtracking are unchanged)
- If speedup is negligible despite large candidate reduction → scanning isn't the bottleneck → informs next steps

## What this tells us

- **If measurable speedup**: Level 2 (explicit neighbor assignment) is worth pursuing. The partitioned data structure is already built; assignment just adds smarter search ordering on top.
- **If no speedup despite fewer candidates**: the bottleneck is elsewhere (backtracking, feasibility). Same signal as 1.2 phase timing, but from a real implementation. Group ordering / symmetry breaking become higher priority.
- **Either way**: the partitioned data structure is useful infrastructure for Level 2/3 and costs nothing to keep.
