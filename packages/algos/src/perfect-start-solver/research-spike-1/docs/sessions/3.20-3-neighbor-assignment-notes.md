# Session 3.20-3: Level 2 neighbor assignment experiment

## What we tried

Level 2 of the neighbor partitioning pipeline: explicit burst→neighbor assignment. Instead of iterating all compatible neighbor partitions at each depth (Level 1), enumerate valid assignments upfront and search within a single partition per depth.

Key changes from Level 1:
- Zero-overlap bursts assigned to specific neighbors before searching
- Assignment enumeration with upfront pruning (skip if partition empty at required length)
- Per-entry processing (no timing-entry grouping/amortization)

## Result: negative

L2-without-grouping is strictly worse than L1 on all board types.

**Corner boards** (degree-2, hard):
| Board | L1 speedup | L2 speedup |
|---|---|---|
| corner-13x13 | 1.41x | 1.24x |
| corner-9x9 | 1.39x | 1.19x |
| floating-corner-11x11 | 1.39x | 1.30x |
| corner-7x7 | 1.28x | 1.12x |

Same 50% candidate reduction as L1, but 10-20% slower due to per-entry overhead.

**Severe regressions** on some boards:
- edge-pocket-9x9: 0.39x (candidates went UP 105%)
- pocket-11x11: 0.39x (3.5M top-level feasibility prunes)
- scattered-pockets-13x13: 0.77x

## Why it failed

### 1. On degree-2 boards, L1 already achieves optimal filtering

After burst-1 claims one neighbor, exactly 1 partition remains (of 2). L1 skips the covered partition — 50% reduction. L2's explicit assignment adds nothing because the assignment is trivially determined (only 1 available neighbor).

### 2. Dropping grouping causes duplicate work

The grouped search amortizes candidate scanning across timing entries with the same (moveLen, overlap) at each depth. L2 processes entries individually, so the same partition gets scanned multiple times (once per entry with the same requirements).

Example: edge-pocket-9x9 candidates went from 323K to 664K (+105%). Two entries needing moveLen=8, overlap=0 at depth 1 each scan the same partition separately.

### 3. Per-entry overhead multiplied by millions

The top-level loop runs per (b1Cand × entry) pair. Each iteration computes burst1Neighbor, runs feasibility checks, and sets up the assignment generator. On boards with many b1Cands and entries (pocket-11x11: 3.5M feasibility checks), even small per-iteration overhead accumulates.

The grouped search does the same feasibility filtering, but through `entries.filter(...)` — tighter code, less overhead per check.

## Could L2-with-grouping work?

In principle: keep the grouped search structure, but sub-bucket entries by their assigned neighbor at each depth. This gives single-partition targeting without duplicate scanning.

On degree-2 boards: equivalent to L1 (only 1 partition available). On degree-4 boards: could help by directing each entry to its assigned partition.

However: our hard boards are all degree-2. Degree-4 boards solve quickly (not candidate-scanning bottleneck). So L2-with-grouping wouldn't help on the boards we care about.

## What about upfront assignment feasibility?

Adding a pre-filter to L1: check if each timing entry has a valid assignment before entering the grouped search. On degree-2 boards, `entryIsFeasibleNeighbors` already catches the same cases (checks zeroOverlapBursts ≤ blankNeighborCount). No additional benefit.

## Conclusion

L2 (explicit assignment) is not the right next step. The gains from assignment structure are theoretical on our board suite — all hard boards are degree-2 where L1 is already optimal.

More promising directions:
1. **Symmetry breaking** — 2x on symmetric degree-2 boards (independent, ~10 lines)
2. **Group ordering** — reorder timing groups by heuristic, attack corner-9x9 bottleneck
3. **Per-neighbor spatial feasibility** — could add to L1 without assignment restructuring
