# Session 3.20-3: Level 2 neighbor assignment experiment

## What we tried

Level 2 of the neighbor partitioning pipeline: explicit burst→neighbor assignment. Instead of iterating all compatible neighbor partitions at each depth (Level 1), enumerate valid assignments upfront and search within a single partition per depth.

Key changes from Level 1:
- Zero-overlap bursts assigned to specific neighbors before searching
- Assignment enumeration with upfront pruning (skip if partition empty at required length)
- Per-entry processing (no timing-entry grouping/amortization)

## Result: negative

L2-without-grouping is strictly worse than L1 on all board types.

**Corner boards** (degree-2, hard):
| Board | L1 speedup | L2 speedup |
|---|---|---|
| corner-13x13 | 1.41x | 1.24x |
| corner-9x9 | 1.39x | 1.19x |
| floating-corner-11x11 | 1.39x | 1.30x |
| corner-7x7 | 1.28x | 1.12x |

Same 50% candidate reduction as L1, but 10-20% slower due to per-entry overhead.

**Severe regressions** on some boards:
- edge-pocket-9x9: 0.39x (candidates went UP 105%)
- pocket-11x11: 0.39x (3.5M top-level feasibility prunes)
- scattered-pockets-13x13: 0.77x

**Degree-3 board** (hard-degree3-9x9, added during session):
- L1: 1.10x, 53% candidate reduction
- L2: 0.88x, 33% candidate reduction
- Board was too easy (~8ms) for meaningful timing comparison, but L1 still showed pure improvement. L2's duplicate scanning hurt even here.

## Why it failed

### 1. On degree-2 boards, L1 already achieves optimal filtering

After burst-1 claims one neighbor, exactly 1 partition remains (of 2). L1 skips the covered partition — 50% reduction. L2's explicit assignment adds nothing because the assignment is trivially determined (only 1 available neighbor).

### 2. Dropping grouping causes duplicate candidate scanning

The grouped search amortizes candidate scanning across timing entries with the same (moveLen, overlap) at each depth. L2 processes entries individually, so the same partition gets scanned multiple times (once per entry with the same requirements).

Example: edge-pocket-9x9 candidates went from 323K to 664K (+105%). Two entries needing moveLen=8, overlap=0 at depth 1 each scan the same partition separately.

### 3. Per-entry feasibility overhead (distinct from #2)

pocket-11x11 shows a different failure mechanism: candidates actually went *down* (145→134), but 3.5M top-level feasibility prunes made it 2.5x slower. The regression is from moving the entry loop outside the search function — every (b1Cand, entry) pair runs feasibility individually, whereas the grouped search batch-filters entries with `entries.filter(...)`.

### 4. Redundant feasibility checks

The top-level feasibility check (lines 303-314 of experiment) and the first `searchWithAssignment` call both check feasibility at burstIdx=1 with the same coveredMask. Wasted cycles on every search entry point.

## Review critique: experiment was designed backwards

The theory doc says the levels are additive (L1→L2→L3). The natural first experiment should have been L1 + assignment (keep grouping, add sub-bucketing by assigned neighbor). By conflating two changes — adding assignments AND removing grouping — we can't isolate whether assignment enumeration itself helps or hurts.

L2-with-grouping would sub-bucket entries by their assigned neighbor at each depth within the existing grouped search. On degree-2 boards this collapses to L1 (trivial assignment). On degree-3+ it could help by directing entries to specific partitions.

The practical conclusion would have been the same (no benefit on degree-2), but the experiment would have been cleaner.

## Other review notes

- **L1 vs L2 comparison was cross-session**: L1 numbers came from the 3.20-2 findings doc, not measured in the same run. Direct three-way comparison would have been more rigorous.
- **`feasibilityEntriesKilled` always zero**: meaningless stat for single-entry search (no entry group to kill from). Should have been removed from the display or noted as inapplicable.
- **No per-depth candidate breakdown**: would have confirmed that duplicate scanning is concentrated at the depths where grouping helps most.
