# Session 3.22-5 — Log

## What happened

**Bug fix: aggregate feasibility check was falsely pruning valid entries on pocket-2-11x11.**

### Background

Session 3.22-4 investigated pocket-11x11 infeasibility and concluded the solver's feasibility check was correct. Daniel suspected pocket-11x11 should be solvable at 24 captures — when that didn't work out (genuinely timing-infeasible), he created pocket-2-11x11 by shrinking the mountain wall from 4 tiles to 3, giving more room. The solver still reported only 23 captures, which was surprising.

Out-of-band work after 3.22-4 (commit dff3bb04) built burst pattern analysis utils and a proof script showing a specific 5-burst pattern achieves 24 captures at exactly tick 50: `[10,5,4,3,2]` with overlaps `[0,3,2,1,0]`. The solver was wrong — this session investigated why.

### Root cause

The solver was finding 0 candidates at cap=24 — all 27,416 search calls pruned by feasibility, 0 candidates checked. Traced to `entryIsFeasibleAggregate` using `blankTilesWithinDist`, which falls back to a heuristic when `dist > FEASIBILITY_MAX_DIST (4)`:

```
beyondTiles = dist - maxDist   // adds 1 tile per BFS ring — massive underestimate
```

For the valid entry at burstIdx=1 after burst 1 (10 straight left):
- Remaining captures: 14, max move length: 8
- Actual blank tiles within dist 8: **36**
- Heuristic estimate: **12** (popcount at dist 4 = 8, plus beyondTiles = 4)
- Check: 12 >= 14? No → falsely pruned

Each BFS ring on an open board adds ~4×radius tiles, not 1. The heuristic underestimates by 3× at dist 8.

### Fix

Replaced the constant `FEASIBILITY_MAX_DIST = 4` with `feasMaxDist = cfg.maxBurst + cfg.maxOverlapPerBurst` (= 15), computed from solver config. This covers the longest possible move length, so the exact precomputed BFS mask is always used and the beyondTiles heuristic is never hit. No extra per-check cost (same array lookup + AND + popcount), just a larger upfront BFS (one-time O(V), negligible).

Updated the two research experiments (3.20-2, 3.20-3) that imported the removed constant to use a local `FEASIBILITY_MAX_DIST = 4` frozen at their original value.

### Results

- **pocket-2-11x11**: 23 → **24 captures**
- All 44 boards: no capture count regressions

### Performance impact

The fix removes false prunes, so boards where cap=24 is genuinely infeasible now do more work exploring it before falling back. Full before/after saved in `tmp/3.22-5-solver-output-{pre,post}-fix.txt`.

Boards that got notably slower (more search work, same capture count):

|-------|---------|----------|
| corner-7x7 | 350ms | 850ms |
| corner-9x9 | 1.1s | 3.5s |
| corner-13x13 | 1.4s | 4.2s |

The old false prunes accidentally sped up infeasible-target boards by short-circuiting at the aggregate check. These boards now correctly explore cap=24 before concluding it's infeasible — exactly the problem Thread 5 (capture-target pre-check) is meant to solve.

Updated `SLOW_SEARCH` in `test-boards.ts` — changed threshold from >500ms to >100ms with heavy search (not path-gen-dominated). Removed half-enclosed-half-open. Added pocket-2-11x11, edge-9x9, semi-open-with-small-pocket. Note: edge-9x9 is a trivial board that shouldn't need 120K candidates — flagged for investigation.

### Corrections to session 3.22-4

Session 3.22-4 concluded "the feasibility check is correct, not over-pruning." This was wrong for pocket-2-11x11 — the aggregate check was over-pruning due to the distance heuristic bug.

For pocket-11x11, the solver still finds 23 after the fix, so the conclusion happens to be correct. However, the experiment (`3.22-4-pocket-11x11-manual-patterns.ts`) that was presented as independent confirmation has a bug: `checkSolution` sorts burst specs ascending by captures before timing simulation, but execution order affects timing — descending (largest first) is faster because longer movement phases accumulate more troops. The experiment tested the worst-case ordering, so its "55 ticks minimum" figure is unreliable. The fixed solver is now the authoritative answer for pocket-11x11, not the experiment.

### Connection to Thread 5

The STATUS "What's next" section specifically called out "root-level feasibility probes with better distance approximations" as a Thread 5 direction. This fix addresses the distance approximation problem directly — though as a correctness bug rather than the optimization angle Thread 5 envisions.
