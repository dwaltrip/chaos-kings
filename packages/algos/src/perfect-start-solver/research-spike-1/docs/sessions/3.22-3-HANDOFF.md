## This session's plan: Thread 5 — Capture-Target Pre-Check

**Goal:** Skip provably infeasible capture targets before entering search. This is the highest-leverage optimization available — 7 of 13 slowSearch boards would see massive speedups.

**Impact estimate from profiling data:**

| Board | Current | Infeasible waste % | Expected after |
|-------|---------|-------------------|----------------|
| tight-corner-2 | 6954ms | 98.9% | ~77ms |
| pocket-11x11 | 3395ms | 99.2% | ~26ms |
| scattered-pockets-13x13 | 3175ms | 98.4% | ~51ms |
| edge-pocket-2-9x9 | 2248ms | 90.8% | ~207ms |
| tight-edge-with-chokes | 1451ms | 98.7% | ~19ms |
| tight-corner-1 | 1047ms | 96.6% | ~36ms |
| edge-pocket-9x9 | 1140ms | 68.1% | ~364ms |

**Specific approaches to try (cheap → sophisticated):**

1. **Total reachable blanks < target → skip.** Count walkable tiles reachable from the general (BFS, one pass). If count < target captures, skip. Cheapest possible — a few lines, O(V+E) once. Should catch tight-corner boards (literally not enough tiles). May NOT catch boards like pocket-11x11 where there are enough tiles but geometry prevents 24 captures.

2. **Root-level feasibility probe.** Before iterating burst-1 candidates, check: with coveredMask = just the general, does ANY timing entry pass feasibility? If all entries fail at root, skip the target. This catches the case where feasibility is 0% pass rate — which is exactly what the data shows for all infeasible targets. Cost: one feasibility sweep per target (not per burst-1 candidate). Could be very cheap since it only needs to check entries in one group.

3. **Per-neighbor capacity check at the target level.** Can the available neighbors collectively support this many captures? Uses existing `NeighborInfo.blankMasks` from L3 infrastructure.

**The thread is open-ended.** These three approaches are starting points. The profiling data may reveal that some boards need different pre-checks, or that a cheap pre-check catches 90% of the waste and the remaining 10% needs a deeper approach. Stay open to unexpected sub-threads — the goal is understanding what makes targets infeasible and how cheaply we can detect that, not just implementing a specific approach.

**Key question to investigate:** Why does pocket-11x11 fail at cap=24? It's an 11x11 board with plenty of tiles. The infeasibility must be geometric (neighbor access, not tile count). This determines whether approach #1 is sufficient or we need #2/#3.
