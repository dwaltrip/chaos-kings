### Thread 5 assessment

Reviewed all Thread 5 work across sessions 3.22-4 through 3.22-6 and analyzed remaining approaches. Concluded that Thread 5 is spent — no viable approach exists for skipping infeasible capture targets cheaply.

The fundamental insight: infeasibility on these boards is **path-level spatial incompatibility** (no compatible paths exist within timing+geometry constraints), not a **capacity shortage** (not enough tiles). Every pre-check approach — reachable tile count, per-neighbor capacity, degree-based filter, root-level feasibility sweep, improved distance approximation — tests capacity in some form. Capacity is never the binding constraint on any current board.

The root-level feasibility sweep (approach #4, not previously implemented) was analyzed and found to be ineffective: the N check at root level is equivalent to the degree filter (already tried), while P and A checks trivially pass with coveredMask=0 since boards have ample tiles.

### Degree filter removal

Removed the degree-based timing entry filter from `solver-v3.ts`. The filter was strictly weaker than the in-search N feasibility check and caused slight performance regressions on some boards (e.g. corner-7x7: 849→1075ms). The `generalDegree` parameter was removed from `buildTimingGroups`.
