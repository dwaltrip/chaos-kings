# Finding: Degree-Based Timing Entry Filter (Thread 5)

**Date**: 2026-03-22
**Session**: 3.22-6
**Verdict**: Correct but ineffective. The filter is strictly weaker than the existing N feasibility check in search, so it kills entries that were already being caught. No meaningful perf impact.

## Idea

Before search, filter timing entries where the total number of zero-overlap bursts exceeds the general's degree (number of walkable neighbors). Each zero-overlap burst must start from a distinct neighbor, so if an entry needs 5 zero-overlap bursts and the general has degree 2, it's impossible.

## Data

Timing entries are board-independent (same config → same entries). Distribution of zero-overlap burst counts at cap=24 (5,425 entries total):

| Zero-overlap bursts | Entries | % |
|---------------------|---------|---|
| 2 | 458 | 8.4% |
| 3 | 2,038 | 37.6% |
| 4 | 2,082 | 38.4% |
| 5 | 757 | 14.0% |
| 6 | 90 | 1.7% |

Kill rates by degree at cap=24:
- **degree 2**: kills 4,967/5,425 (91.6%)
- **degree 3**: kills 2,929/5,425 (54.0%)
- **degree 4**: kills 847/5,425 (15.6%)

**13 of 14 slow boards have degree 2.** tight-corner-2 has degree 1.

At lower capture targets, kill rates drop (63.8% at cap=23 for degree 2, 48.7% at cap=22).

## Why it doesn't help

The existing N feasibility check inside `searchGrouped` already catches these entries — and more. After B1 runs:
- B1 consumes one neighbor (always overlap=0)
- B1's path may cover additional neighbor tiles, further reducing `blankNeighborCount`
- The in-search N check sees `K-1` remaining zero-overlap bursts vs `blankNeighborCount ≤ degree-1`

The degree filter checks `K ≤ degree`, which is equivalent to `K-1 ≤ degree-1` — strictly weaker than `K-1 ≤ blankNeighborCount` since `blankNeighborCount ≤ degree-1`.

Every entry killed by the degree filter was already being killed by the in-search N check. The filter only saves iterating those entries in the feasibility loop, but each iteration is trivial (count + compare).

**Crucially, the degree filter cannot skip entire capture targets on degree-2 boards.** At cap=24, 458 entries (8.4%) have only 2 zero-overlap bursts and survive. The solver still iterates all B1 candidates and checks those survivors. Only degree-1 (tight-corner-2) gets a full target skip at cap=24.

## Runtime comparison

Entry counts drop substantially but runtimes are flat:

| Board | Baseline | With filter | Entries before → after |
|-------|----------|-------------|----------------------|
| half-enclosed-half-open | 42ms | 25ms | 17,933 → 1 |
| pocket-2-11x11 | 563ms | 504ms | 22,987 → 6,457 |
| pocket-11x11 | 2017ms | 2128ms | 18,004 → 7,470 |
| corner-7x7 | 849ms | 1075ms | 36,388 → 11,370 |
| corner-9x9 | 3481ms | 3834ms | 50,545 → 14,497 |

Search calls and candidate counts are identical — confirming the filtered entries contributed zero useful work.

## Disposition

Kept in solver with a TODO to consider removal. The filter is correct and near-zero cost, but adds no perf value. If a future change makes the N feasibility check more expensive per-entry, this pre-filter would become worthwhile.
