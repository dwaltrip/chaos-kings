# Finding: 1.3 Path Mask Redundancy

**Date**: 2026-03-20
**Session**: 3.20-1
**Verdict**: Mask redundancy is minimal. Dedup is not a meaningful optimization lever.

## Summary

We measured how many generated paths share identical bitmasks across all 28 test boards, at every path length 1–12. The hypothesis (from the exploration survey) was that open boards would show 10–50x compression — many tile orderings producing the same mask. The actual result: **1.1–1.4x across all boards, all lengths**. There are no dominated masks (strict subsets) anywhere.

## Key numbers

| Board type | Overall ratio | Peak ratio | Peak length |
|---|---|---|---|
| Open boards (7x7–13x13) | 1.2–1.3x | 1.3–1.4x | 11–12 |
| Constrained (corridors, walls) | 1.2–1.4x | 1.4–1.5x | 9–12 |
| Highly constrained (mazes, pockets) | 1.0–1.2x | 1.1–1.4x | varies |

Specific headline numbers:
- **open-11x11, len 12**: 178,552 paths → 143,338 masks = **1.2x**
- **open-13x13, len 12**: 252,992 paths → 208,590 masks = **1.2x**
- **corner-9x9, len 12**: 60,146 paths → 50,188 masks = **1.2x**
- **pinch-9x9** (highest overall): 36,652 paths → 26,680 masks = **1.4x**

## Class size distribution

The vast majority of masks are unique (class size 1). On open-11x11 at length 12: 122,336 masks with exactly 1 path, 20,218 with 2–5 paths, 784 with 6–20 paths. Zero masks with 21+ paths. There are no large equivalence classes to exploit.

## Overlap-aware classes

Adding prefix information (tiles[0..k] for k=1,2,3) barely inflates the class count beyond pure mask dedup. Example — open-11x11, len 12:

| Grouping | Distinct classes |
|---|---|
| Mask only | 143,338 |
| Mask + prefix-1 | 144,672 (+0.9%) |
| Mask + prefix-2 | 147,476 (+2.9%) |
| Mask + prefix-3 | 147,932 (+3.2%) |

This means overlap handling doesn't meaningfully erode the (already small) dedup gains.

## Dominated masks

**Zero across all boards, all lengths.** No path mask at length L is a strict subset of another mask at the same length. This makes sense in hindsight: the DP generates all non-backtracking paths, so a path of length L always visits exactly L tiles. Two different L-tile masks from different paths through a grid almost never have a subset relationship — they tend to diverge spatially.

## Why the hypothesis was wrong

The survey expected that on open boards, many tile orderings would produce the same mask — e.g., capturing tiles {A, B, C, D} in different orders. But the DP generates **non-backtracking paths from the general**, not arbitrary subsets. A path must be a connected chain of adjacent tiles with no revisits. On a grid, two different orderings of the same tile set usually require different spatial routes, and different routes cover different tiles. The constraint that paths are contiguous chains means path ↔ mask is nearly 1:1.

The small amount of redundancy that does exist (the 1.1–1.4x) comes from cases where two paths reach the same endpoint set via slightly different routes that happen to visit the same tiles — e.g., going right-then-down vs down-then-right through a 2×2 block.

## Implications

### What this rules out
- **Path dedup (4.1)** as a significant optimization. A 1.2x reduction isn't worth the code.
- **Inverted index search** (from the critical review) — depended on large domain reduction from dedup.
- **Arc consistency** becoming cheap via dedup — domains stay large (50K–200K), so O(d²) pairwise pruning remains expensive.

### What this tells us
- The path set is already nearly minimal in mask-space. The solver's redundant work comes from somewhere else — likely trying many spatially-similar-but-not-identical masks in the same region.
- **Coverage clustering (4.2)** — grouping near-duplicate masks by spatial similarity — may still have value, since the 143K distinct masks on open-11x11 likely contain many near-neighbors (Jaccard > 0.8). But this is a different, harder optimization than exact dedup.
- The focus should shift to **search structure** improvements (pruning, ordering, sector awareness) rather than **candidate set reduction**.

## Follow-up: Starting-neighbor distribution

We also measured how paths distribute across the general's neighbors (`tiles[0]`).

**Symmetric boards** (open, corner, pinch) split perfectly evenly — 25% per neighbor (degree 4) or 50% (degree 2). No surprise.

**Asymmetric boards** show significant imbalance:
- **off-center-13x13**: 38%/35%/16%/11% — the most open direction has 3.5x more paths than the most constrained
- **narrow-corridors-11x11**: 55%/28%/17% across 3 neighbors
- **edge-9x9**: 46%/27%/27% — the inward neighbor dominates
- **pocket-11x11**: 62%/38%
- **island-11x11**: 39%/23%/23%/16%

The imbalance grows with path length — at length 12, dominant neighbors often have 2–4x more paths than weak ones. This makes sense: longer paths need more room to snake without self-intersecting, so they preferentially go through whichever neighbor has the most open territory behind it.

### Tentative insight: direction-based candidate partitioning

Each zero-overlap burst must start through a distinct neighbor (two zero-overlap bursts can't share a first tile — they'd overlap). Once the solver commits a burst to a specific neighbor, only paths starting through that neighbor are relevant candidates. Today the solver scans all paths and most fail the overlap check — but many of those failures could be skipped upfront by just checking `tiles[0]`.

On asymmetric boards, this could be significant. If the solver is searching for a burst through the weakest neighbor on off-center-13x13, ~89% of paths start through a different neighbor and could be skipped without any mask check. Even on mildly asymmetric boards, partitioning candidates by starting neighbor cuts the scan by (1 - 1/degree) — 75% for degree-4, 50% for degree-2.

This is the simplest concrete form of the "directional awareness" that the research spike is exploring. It doesn't require sector decomposition or fuzzy affinity — just grouping paths by their first tile. Whether this actually speeds up the solver depends on whether the inner loop is bottlenecked on candidate scanning (where this helps) vs backtracking over timing entries (where it doesn't). Worth testing, but not yet validated.
