# Finding: 3.2 Neighbor Partitioning (Level 2) & Revised Pipeline

**Date**: 2026-03-21
**Session**: 3.20-3
**Verdict**: L2 (explicit neighbor assignment without grouping) is a negative result. However, the investigation clarified the full pipeline design and identified the correct implementation path.

## L2 experiment summary

Implemented Level 2 as described in the theory doc (`sessions/3.20-2-neighbor-partitioning-levels.md`): enumerate burst→neighbor assignments for zero-overlap bursts, search within a single partition per depth. Compared against baseline solveV3 across all 28 boards.

**Result**: Slower than L1 on every board. Same 50% candidate reduction on corner boards but 10-20% slower. Severe regressions on some boards (edge-pocket-9x9: 0.39x, pocket-11x11: 0.39x).

**Root cause**: The implementation dropped timing-entry grouping, which caused duplicate candidate scanning across entries and per-entry feasibility overhead. This was a design error — the theory doc says levels are additive, so grouping should have been preserved.

See `sessions/3.20-3-neighbor-assignment-notes.md` for detailed failure analysis and review critique.

## Key insight: L1 is already optimal on degree-2 boards

On degree-2 boards (all our hard boards), after burst-1 claims one neighbor, exactly 1 partition remains. L1 skips the covered partition — 50% reduction. No variant of L2 (with or without grouping) can improve on this. The assignment is trivially determined.

On a degree-3 test board (hard-degree3-9x9, added during session), L1 showed 53% candidate reduction and 1.10x speedup even on a fast board (~8ms). L2 showed 33% reduction and 0.88x (duplicate scanning from dropped grouping).

## Revised pipeline

The original theory doc presented a linear progression: L1 → L2 → L3. Based on the L2 experiment and subsequent analysis, the practical pipeline is:

### L1: Partition and filter (proven)

Partition candidates by starting neighbor. Skip irrelevant partitions based on coveredMask. 1.28–1.41x on hard corner boards, 50% candidate reduction.

**Overhead can be reduced** for production integration:
- Precompute neighbor bits (avoid `1n << BigInt(neighbor)` per depth)
- Use arrays instead of Maps for the partition structure (degree is 2-4)
- This would make L1 closer to pure win even on easy boards (currently shows mild regression on some)

### L2: Explicit assignment with grouping (available, low priority)

Keep the grouped search structure from L1. Sub-bucket entries by assigned neighbor at each depth. Each sub-bucket searches a single partition.

On degree-2: collapses to L1 (trivial assignment, 1 sub-bucket). On degree-3+: could help by directing entries to specific partitions and enabling upfront assignment pruning. Only worth implementing if hard high-degree boards emerge.

**Important**: Must preserve grouping. The L2-without-grouping variant tested in session 3.20-3 is strictly worse — do not revisit.

### L3 pruning: Per-neighbor spatial feasibility (promising, independent of L2)

Natural extension of the existing `blankTilesWithinDist` check. Precompute per-neighbor reachable tile masks:
- BFS from each neighbor (2-4 of them), excluding the general tile, cumulative masks by distance
- Store as `neighborBlankMasks[neighbor][d]`

At search time, for a zero-overlap burst through neighbor B with moveLen M and captures C:
```
popcount(neighborBlankMasks[B][M-1] & ~coveredMask) >= C
```

One bigint operation per check. **Strict prune, not heuristic.** Catches cases where global feasibility passes ("enough tiles overall") but per-neighbor fails ("not enough tiles through B specifically").

Applies directly to L1's partition loop — no L2 dependency. Precomputation is cheap: 2-4 BFS traversals, each O(board_size), done once per solve.

### L3 heuristic: Partition ordering by spatial capacity (research territory)

Order neighbor partitions by spatial capacity — try the most promising direction first. A timing entry with captures [12, 4, 4] should try the neighbor with the deepest territory first for the 12-burst.

This doesn't reduce worst-case work, but reduces expected work by finding solutions earlier. Requires defining "spatial capacity" per neighbor (BFS sector size, reachable tiles within distance budget, etc.) and validating that the heuristic correlates with solution likelihood.

This is the entry point to the sector awareness that the research spike is ultimately about.

## How they compose

| Level | Depends on | Adds | Win type |
|---|---|---|---|
| L1 | — | Partition + filter | Fewer candidates iterated |
| L2 | L1 | Sub-bucket by assignment | Single-partition targeting (degree-3+) |
| L3 pruning | L1 | Per-neighbor feasibility masks | Strict spatial pruning |
| L3 heuristic | L1 | Partition ordering | Earlier solution discovery |

All levels share the `PartitionedEntries` data structure. L2, L3 pruning, and L3 heuristic are independent of each other — any combination works. All are orthogonal to symmetry breaking and group ordering.

## Recommended next steps

1. **Integrate L1** into the main solver with reduced overhead (precomputed bits, arrays)
2. **L3 pruning** — per-neighbor feasibility via `neighborBlankMasks`. Independent of L2, cheap to implement, strict benefit
3. **Symmetry breaking** and **group ordering** — independent quick wins, stack with everything
4. **L2 proper** — only if hard degree-3+ boards appear in the test suite
