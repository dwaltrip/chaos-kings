# Finding: L3 Per-Neighbor Spatial Pruning

**Date**: 2026-03-21
**Session**: 3.21-1
**Verdict**: Zero additional prunes on all 29 test boards. Correct implementation, but the geometry that triggers it doesn't appear in the current test suite. Kept in solver — cheap insurance.

## What it does

For zero-overlap bursts through neighbor B with moveLen M, check whether B's reachable territory has enough blank tiles for the required captures:

```
popcount(nb.blankMasks[moveLen - 1] & ~coveredMask) >= captures
```

This is a strict prune (not heuristic). It catches cases where global feasibility passes ("enough tiles overall") but per-neighbor fails ("not enough tiles through B specifically").

Applied in L1's partition loop, after the neighbor coverage check but before iterating candidates. One bigint AND + popcount per neighbor per bucket — negligible cost.

## Precomputation

BFS from each neighbor (2-4 of them), excluding the general tile, cumulative masks by distance. Stored as `NeighborInfo.blankMasks`. Computed once per solve.

As part of this work, the BFS was extracted into a shared `board-bfs.ts` utility (`bfsCumulativeMasks`), which is now used by both the per-neighbor BFS and the existing global `precomputeBlankTileDistMasks`.

## Why zero prunes

The check is strictly tighter than global `entryIsFeasiblePerBurst` only when a specific neighbor's territory is more constrained than the total board. On current test boards, this doesn't happen:

1. **Degree-2 corner boards** (all the hard boards): After burst-1 covers one neighbor, L1 already filters to the single remaining neighbor. That neighbor has access to roughly half the board — far more reachable tiles than any burst needs. Per-neighbor feasibility adds nothing over global feasibility.

2. **Open/large boards**: Every neighbor has enormous territory. The per-neighbor check trivially passes.

3. **Constrained boards that are already easy**: Corridors, mazes, mountains — these solve quickly already (few candidates). Higher-level feasibility checks already handle pruning.

## When it would fire

A board where:
- Neighbor A opens to a large area (many reachable tiles)
- Neighbor B opens to a narrow corridor or small pocket (few reachable tiles)
- Global feasibility passes because A's territory makes the total count sufficient
- Per-neighbor check catches that a burst assigned to B can't fit in B's territory

This requires **asymmetric neighbor territories** — not present in the current test suite. A future test board with this geometry (e.g., general at the mouth of a corridor with open space on the other side) would demonstrate the prune.

## What we gained regardless

Even with zero prunes, the implementation work produced:
- `board-bfs.ts` — shared BFS utility, useful for future spatial analysis
- `NeighborInfo.blankMasks` — per-neighbor spatial data, available for future heuristics (e.g., partition ordering by territory size for the L3 heuristic idea)
- Cleaner solver code via BFS deduplication

## Broader signal

The zero-prune result, combined with the L2 negative result, suggests that **per-neighbor spatial feasibility is not the binding constraint** on current test boards. The bottleneck is combinatorial — too many compatible candidates to search through — not spatial. This points toward ordering/early-termination approaches (symmetry breaking, group ordering) as higher-leverage next steps than tighter spatial bounds.
