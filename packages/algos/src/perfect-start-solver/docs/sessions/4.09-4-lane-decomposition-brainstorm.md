# Lane Decomposition — Brainstorm Reference

Brainstorm catalog for the mid-region lane decomposition problem. This is the least-understood and highest-leverage piece of the next-gen solver framework: given a prefix set with 2-3 tips pointing into the board, how do we decompose the mid-region into non-overlapping, non-backtracking lanes so the corridor model applies?

## Problem statement

**Input:** A contiguous blob of already-claimed tiles on a grid board (representing the near-region / prefix territory), plus the surrounding board with mountains as obstacles.

**Output:** k non-overlapping, non-backtracking lanes extending outward from the blob's surface, each meeting a target length.

**Staged approach:** This is intentionally framed as a relaxed, blob-only formulation meant to reveal tractability and power of decomposition strategies in isolation. The blob is an opaque shape; the decomposition doesn't need to know how it was constructed.

A solver-usable version will also need:
- **Admissible entry points** — in the full solver, bursts enter the mid-region through specific prefix tips, not arbitrary surface tiles. This constrains which decompositions are actually valid.
- **Entry overhead accounting** — each lane has a traversal cost from the general to its entry point (the overlap/frontier concept from the corridor model). The downstream corridor DAG needs this per lane.

These are deferred from the initial exploration phase. If the relaxed decomposition already looks hard, fold the full constraints in immediately. If it looks strong, integration may be a straightforward follow-up step.

A valid lane decomposition (in the relaxed formulation) satisfies:
- **Non-overlapping** — each tile belongs to at most one lane (guarantees lane independence)
- **Non-backtracking** — each lane is a simple path (no repeated tiles) that a burst can advance through
- **Sufficient length** — each lane meets its target length (we don't need to cover the full mid-region, just provide enough depth per lane)

## The "good enough" principle

The decomposition doesn't need to be comprehensive or optimal. Most boards have many equally-optimal solutions, so the decomposition just needs to *contain* at least one optimal solution's paths — not perfectly partition all reachable space.

**Surface area tradeoff:** Blobs with large surface area have many candidate entry points for lanes — many good options exist, so decent heuristics should suffice. Blobs with small surface area have fewer options and require more careful partitioning to avoid missing an optimal solution, but the search space is smaller, which hopefully will keep things quite tractable.

## Approach catalog

### Analytical / feasibility

**Face projection.** Ray-cast outward from each cardinal face of the blob, measure unobstructed depth per ray. Gives per-direction capacity stats: face width, min/max/avg depth, total tiles covered. An 8-region framing falls out naturally — 4 cardinal regions (directly off each face) and 4 diagonal regions (off each corner). Cardinal regions are straightforward; diagonal regions are where routing decisions concentrate. Cheap to compute, good first-pass feasibility filter. Doesn't handle terrain that requires non-straight routing.

**Max-flow / min-cut.** Model the blob surface as a source and the mid-region far boundary as a sink. Max-flow gives the capacity ceiling on how many non-overlapping lanes the terrain can support. Min-cut reveals where the bottleneck is. Cheap on small grids. Doesn't construct lanes, but instantly answers "can this region support k parallel lanes?" — if not, skip this prefix set without doing any construction.

### Structural analysis

**Skeleton / medial axis.** Thin the mid-region to its spine — the set of tiles maximally distant from obstacles/boundaries. Shows natural highways through the region. Wide sections (thick skeleton) can support multiple parallel lanes; narrow sections (skeleton near boundary) are pinch points where lanes must converge to single-file. Could guide lane placement — build lanes along or parallel to the skeleton.

**Obstacle-gap / dual perspective.** Instead of routing through open space, identify the gaps between obstacles (mountains, blob tiles, board edges). Natural corridors emerge from the negative space between obstacles. On constrained boards (where the solver needs the most help), the obstacle structure may directly dictate the lane layout.

### Constructive

**Territory partition + path-finding.** Two sub-problems:

*Assignment* — which tiles belong to which lane's territory:
- Voronoi / weighted Voronoi — assign each tile to its nearest tip, optionally weighted by lane length needed (tips requiring longer lanes get more territory). Simple, proximity-based.
- Graph partitioning — broad family of formal methods (spectral, flow-based, geometric, multi-level coarsening, etc.). Standard objectives (min-cut, balanced size) don't directly match our needs (connected territories with sufficient depth per tip), but the techniques may adapt.
- Simpler heuristics as needed.

*Path-finding within territory* — turn an assigned blob of tiles into an actual lane:
- Contour-parallel / hugging — lane 0 extends from the entry point, lane k+1 hugs adjacent to lane k. Borrowed from CNC toolpath planning / coverage path planning in robotics. Adapts to terrain curvature naturally.
- Greedy extension — extend from entry point as far as possible within the territory.

Territory assignment guarantees non-overlap between lanes. Path-finding determines lane shape and length.

**Greedy longest path.** Skip territory assignment entirely. Process tips in priority order (longest lane needed first), greedily extend each as far as possible, mark tiles as used. Simpler but order-dependent — a degenerate case where territory assignment and path-finding happen simultaneously. Fast and may work well enough given the "good enough" principle.

**Random sampling.** Generate random non-backtracking paths from each tip, check for non-overlap, keep the best. Monte Carlo approach. Surprisingly viable when k is small (2-3) and the mid-region has many tiles. Could serve as a baseline or complement to more structured methods.

### Direct search

**Vertex-disjoint paths.** Formulate the problem directly: find k non-overlapping paths of specified lengths L1..Lk from specified entry points T1..Tk. Related to the well-studied k-disjoint-paths problem in graph theory (Robertson-Seymour proves polynomial-time solvability for fixed k on general graphs). However, our variant — with specified path lengths and free far endpoints — is not directly covered by those results, and the general-theory algorithms have impractical constants. On grid graphs with k=2-3, more practical approaches likely exist but would need to be found or built. Still, this is the most direct translation of what we actually need — no territory assignment or partitioning, just find the paths.

**CSP / SAT.** Model as a constraint satisfaction problem. Variables = tile-to-lane assignment. Constraints = each lane forms a connected non-backtracking path from its entry point, lanes don't share tiles, each lane meets its length target. Heavyweight but exact — useful as a reference implementation or for validating heuristic approaches.

## Composition — how approaches pipeline together

These approaches aren't all competing — many serve different roles and compose into a pipeline:

1. **Feasibility filtering** — max-flow / min-cut quickly eliminates prefix sets where the terrain can't support enough parallel lanes. Face projection gives directional capacity stats.
2. **Structural understanding** — skeleton / obstacle-gap analysis reveals the natural routing structure and bottlenecks.
3. **Lane construction** — territory partition + path-finding, greedy, or random sampling to actually build the lanes.
4. **Validation / exact solving** — vertex-disjoint paths or CSP as a fallback or reference for hard cases.

The right pipeline likely depends on board geometry. Constrained boards (where the solver is slowest) may have near-obvious decompositions from the obstacle structure alone. Open boards (where the solver is already fast) have more freedom and may need more exploration, but also tolerate approximation.

## Decomposition reuse across timing entries

A decomposition with high capacity (most lanes, longest lanes) can likely serve many or most timing entries for a given prefix set. Rather than re-decomposing per timing entry, the strategy may be: find the "best" decomposition that maximizes available lane count and length, then check which timing entries it can accommodate. The decomposition becomes a property of the prefix set + board geometry, not of individual timing entries.

- How often do real boards produce blobs where decomposition is genuinely hard (tips pointing into overlapping regions, narrow funnels)?
